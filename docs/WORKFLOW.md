# 시험 중 실행과 검증

## 시작

과제 README와 기존 지침을 읽고 루트·필수 제출물·금지 변경·완료 조건을 확인합니다.
이미 제시된 문제와 솔루션은 구체화해서 첫 실행으로 이어갑니다. 도메인이 낯설면
domain-discovery와 data-quality로 용어·단위·업무 정책의 근거를 먼저 연결합니다.
질문은 결과를 바꿀 미확인 정책에 집중하고 독립적인 실행·조사는 진행합니다.

선택한 Skill은 `scripts/setup.py`, MCP는 `scripts/mcp_config.py`로 준비합니다.
MCP 없이도 진행할 수 있어야 합니다. 선택·제외한 도구의 이유와 실제 효과를 WORKLOG에 적습니다.

## 구현

가장 작은 입력→처리→출력 경로를 먼저 연결합니다. 기존 인터페이스와 스택을 우선 사용합니다.
독립 작업은 계약·소유 파일·완료 검증을 정해 나누고 도착한 결과부터 통합합니다.
공통 계약·의존성·상태·최종 통합은 주 에이전트가 관리합니다.

## 검증 기록

기존 프로젝트의 테스트·실제 실행을 우선 사용합니다. 정상·중요 실패 경로를 확인하고,
도메인의 불변조건·경계·단위·데이터 건수를 필요한 만큼 검증합니다.
단위·mock·로컬 통합·실제 외부 연동·직접 UI 확인·미실행을 구분합니다.

검증 명령을 반복 기록해야 할 때 `templates/CHECKS.json`을 실제 과제에 맞게 채웁니다.
`source_paths`는 변경할 코드, `fixed_paths`는 비교 기준인 테스트·입력·기대값입니다.
`checks`에는 `id`, `kind`, `argv`, `timeout_seconds`를 넣습니다.
필요하면 `stdout_json_file`로 실제 출력과 기대 JSON을 비교합니다.
설정 파일의 경로 기준은 설정이 있는 폴더입니다. 명령은 shell 없이 실행됩니다.

```sh
python3 /가져온/toolkit/scripts/run_checks.py --config /실제/과제/CHECKS.json --stage baseline
python3 /가져온/toolkit/scripts/run_checks.py --config /실제/과제/CHECKS.json --stage verify --baseline /실제/baseline/manifest.json
```

빈 CHECKS.json은 완성된 검증이 아닙니다. 실제 검증을 채운 뒤 실행하세요.
중요한 실제 결함은 같은 검증의 실패→수정→통과로 연결합니다. 테스트·입력·기대값이
달라졌다면 새 기준선을 만듭니다. 증거용 결함이나 협업 기록을 꾸미지 않습니다.
해시는 선언한 파일만 다루고 로그 마스킹도 제한적이므로 출력 자체를 최소화합니다.

## 마무리

최종 제출 루트에 필수 파일을 통합하고 저장 상태와 관련 검증을 확인합니다.
실행 명령·주요 파일·데이터 흐름·중요한 결정·한계·미검증 범위를 DELIVERY나 요구 문서에 적습니다.
MCP memory를 사용했다면 WORKLOG와 실제 구현을 대조합니다. 저장된 기억을 정답으로 취급하지 않습니다.
서술형 전에는 본인이 이유·위치·근거·실패 조건을 설명할 수 있는지 확인합니다.
AI 사용 금지 단계에서는 이 도구들을 사용하지 않습니다.
